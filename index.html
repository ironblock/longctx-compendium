—archetypes · 3 views + build-value
Prefill is a per-event cost, not a per-turn cost. No inference server worth using re-prefills the whole context every turn in an active session — the KV cache from earlier turns stays hot, and only newly appended tokens get processed. What caching does not erase: for full/quadratic attention, each new token still has to attend across the entire existing cache, so the marginal cost of the next turn keeps growing with session depth even though nothing is literally re-prefilled — that's the same slope as the Prefill falloff curve below, just read as a per-turn cost instead of a cold-start one. Linear/hybrid attention (Mamba2, Gated DeltaNet) is what actually escapes that scaling — see the Strix Halo note in Method & sources. Cold-start wall-clock is what a session start, a cache eviction, or a mid-prefix edit costs. Steady-state turn is what turn 50 of an otherwise-untouched session costs — the number that actually governs an active agentic loop.

Theoretical maximum: roofline ceiling what the catalog's own OPS + bandwidth numbers say a unit COULD do — before any benchmark

Every measured number above sits below some physical ceiling: for a chosen model and storage quant, prefill is bounded by the unit's rated compute throughput and decode is bounded by its memory bandwidth. This table computes both ceilings straight from the hardware catalog — no benchmark involved — assuming perfect (100%) utilization, so nothing real should ever exceed it. A measurement that DOES exceed its own ceiling (see tools/roofline-check.mjs) means something in its attribution is wrong, not that the hardware is unusually fast. Compute-precision-per-quant is currently the documented-safe floor (dequantize to FP16) everywhere a per-architecture native fast-path hasn't been separately grounded — see docs/roofline-dequant-paths.md — so a quant/architecture combo with a real faster native path (e.g. NVFP4 on Blackwell) will show a ceiling here that is lower than the true one, never higher.

Method & sources

  • Prefill curves: B70 (llama.cpp SYCL, PMZFX/intel-arc-pro-b70-benchmarks) and AMD R9700 (ggml discussion #19890, Q4_K_XL, Q4_K_M) are the best-measured at ≥4 context points. RTX 5090 MoE (hardware-corner.net, Q4_K_XL) provides 4 points. Mac M3 Ultra dense (mlx discussions #3209, mlx_lm.benchmark) provides 3 points. DGX Spark (DandinPower/llama.cpp_bench; NVIDIA Dev Forums) and Strix Halo (Level1Techs; strix-halo-guide) have 2 anchors each; remainder extrapolated.
  • RTX PRO 6000: pp512 7,640 and tg 251.6 from llm-tracker.info (Q4_K_M, 30B-A3B). NVFP4+MTP dual-card figures from loftllc.dev (~190 t/s tg) and theogravity/dual-rtx-6000-blackwell-qwen3.6-27b-fp8. Dense proxy from vaditaslim.com (Qwen2.5-32B Q4_K_M). JarvisLabs confirms 1.73× MTP gain on dense. vLLM issue #27649 warns of 55s TTFT footgun (misconfiguration; fix = correct BF16 flags). gpt-oss-120B prefill peaks at 4-8K (~24K t/s) then falls off — the rise from 512→4K is typical for vLLM MXFP4 where short-context kernel launch overhead dominates before memory bandwidth becomes the limiter.
  • DGX Spark: gb10 community confirms 273 GB/s shared SoC bandwidth; dense 32B decode confirmed bandwidth-wall-limited at ~10.7 t/s (theoretical ~15). "~1 PFLOP" is sparsity figure (~500 effective dense TFLOPS). Qwen3.5-35B-A3B TTFT/tg from NVIDIA Dev Forums (claytantor, Apr 2026).
  • Strix Halo: Use Vulkan/RADV, not ROCm (ROCm hangs on Qwen3.5 load_tensors). Set HSA_OVERRIDE_GFX_VERSION=11.5.1. Level1Techs/lhl thread and strix-halo-guide are primary sources. DeltaNet hybrid attention keeps long-context KV growth nearly flat: 4K→32K adds only 560 MB KV, tg drops 53.7→49.9 t/s.
  • Multi-GPU 3090: 2-way NVLink gives ~48% TP throughput boost over PCIe-only; 4-way (two bridged pairs over PCIe) only ~8–10% and can lower single-request decode (71→53 t/s on QwQ-32B). dzombak.com: 2× 3090 TP-2 runs Qwen3.6-27B AWQ at ~100 t/s full 256K ctx. Medium/fzbcwvv: 1× 3090 + MTP on Qwen3.6-27B reaches 85–106 t/s at 230 W cap.
  • Cold-start wall-clock: TTFT = context_length ÷ pp(context_length). Wall-clock for a 16K+2K turn = TTFT@16K + (2048 ÷ tg). This is a cold (un-cached) monolithic prefill from empty — what a session start costs, a cache eviction, or a mid-prefix edit (anything that busts the KV cache). It is not what turn 50 of an otherwise-untouched session costs.
  • Steady-state turn: an active session's KV cache stays hot turn to turn, so nothing re-prefills the existing context — but for full/quadratic attention, each newly appended token still attends across the entire existing cache, so the marginal cost of the next turn keeps growing with session depth even though nothing is literally re-prefilled. That marginal rate is derived from the same prefill-curve data already on this page: cumulative time to reach each context checkpoint (tokens ÷ pp) is differenced between consecutive checkpoints to get the local tokens/sec for appending within that range, rather than needing a separate incremental-append benchmark that doesn't exist yet. The steady-state chart appends 2K tokens onto a session already 16K deep (using the 16K→32K segment's marginal rate) and generates 2K more — same turn size as the cold chart, so the two are directly comparable. Linear/hybrid attention (Mamba2, Gated DeltaNet — see the Strix Halo note above) is the one thing that actually escapes this scaling; its marginal rate stays close to flat regardless of session depth.
  • AMD R9700 included as bonus: Strong Qwen3.5-35B-A3B MoE numbers, R9700 single-card, Q4_K_XL (ggml #19890). Not in the user's original list but data quality warranted inclusion.
  • Compute throughput by precision: each unit's compute.values entries come from vendor datasheets/whitepapers where available, with per-unit provenance in compute.source and sources[] — see the hardware catalog table above. Coverage is intentionally uneven: about half the catalog has a real multi-precision breakdown (RTX PRO 6000, RTX 5090, Radeon AI PRO R9700, MI300X, MI355X); several NVIDIA data-center units (V100, A100, H100) currently show only FP64/FP32/FP16 because the Wikipedia Tesla template they're sourced from doesn't publish more, not because the silicon lacks BF16/INT8 paths — exactly the "double, single, half" flattening this chart exists to see past. Filling in the rest is ongoing.
  • Editing this page: every number lives in data/compendium.json. See data/README.md for how to add a device or a datapoint.
