## 1. Lead correction — the `dense` archetype is not full-attention, and the page's architecture thesis is computed from a hybrid model

**Now:**
- `data/compendium.json:38-39` — `meta.archetypes[id=dense]` = `{"label": "Full-attention dense", "desc": "Full-attention dense · Qwen3.x-27/32B Q4 · all weights read per token"}`
- `data/compendium.json:2521-2526` — `long_context_falloff.findings[4]` = `{"architecture": "Dense full-attention", "model": "Qwen3.5-27B", "pp_512": 869, "pp_32k": 614, "falloff_rating": "quadratic"}`
- `data/compendium.json:2499-2504` — `findings[2]` = `{"architecture": "Full-attention MoE", "model": "Qwen3.5-35B-A3B", "falloff_rating": "quadratic"}`

**Wrong.** Qwen3.5/3.6 is hybrid Gated DeltaNet, not full attention. Source-verified in two independent checkouts: `llm_arch_is_hybrid()` in `/Users/corey/git/reference/llama.cpp/src/llama-arch.cpp:934-952` (and `beellama.cpp` :992-1010) is an exhaustive switch returning true for `LLM_ARCH_QWEN35` and `LLM_ARCH_QWEN35MOE`, alongside `QWEN3NEXT`, `KIMI_LINEAR`, `NEMOTRON_H`; `LLM_ARCH_QWEN3` and `LLM_ARCH_QWEN3MOE` are absent and fall to `default: return false`. Confirmed live: a production beellama server logs `srv speculative_: flat DFlash target architecture qwen35 will use recurrent-only backup cells`.

**Should say.** "Dense" is true in the non-MoE / all-weights-active sense; "full-attention" is a separate claim and it is false for the Qwen3.5/3.6 members. Rename the archetype to something true of all members (`label: "Dense (non-MoE)"`, `desc: "Dense · Qwen2.5/3.x-24–32B Q4 · all weights read per token"`), move attention class to a per-platform field (`perf.<arch>.attention: "full" | "hybrid-gdn"`), set `findings[4].architecture` to `"Gated DeltaNet hybrid (dense)"` and `findings[2].architecture` to `"Gated DeltaNet hybrid MoE"`, and drop the `"quadratic"` causal ratings — whatever produced −29% and −19% on that V100, full-attention quadratic growth is not available as the explanation.

**Why this is the lead, not a nitpick.** `meta.archetypes[].desc` is interpolated verbatim into all four chart captions (`assets/data.js:192` → `assets/verdicts.js:108-113` `captionFor` → `assets/app.js:61-64`), so every dense prefill/decode/wall-clock/steady-state chart carries the false attention claim. The compendium's quantitative proof that dense full-attention falls off harder than Gated DeltaNet is computed from a Gated DeltaNet model.

The file already knows the concept — `findings[1]` correctly tags Qwen3-Next-80B-A3B as `"Gated DeltaNet hybrid"`. It drew the generation boundary in the wrong place. **Note the boundary carefully: Qwen3-32B (`LLM_ARCH_QWEN3`) is genuinely full-attention.** Only the 3.5/3.6 rows are mislabeled.

## 2. Architecture & labeling — downstream instances

## 4. Derivation logic (`assets/*.js`)

**C1. The steady-state chart prices its 2K generation at the short-context decode rate.** `assets/derive.js:169` — `const gen = genTokens / tg.v;` where `tg.v` comes from `decode.short` (`assets/data.js:52,58`). The generation term is **81-98% of every bar**. The depth-resolved figure `decode.at32k` is loaded (`data.js:60`), charted (`charts.js:136-137`, legend `tg @32K+ (measured)`) and tabled (`tables.js:126-128`) — and `grep` confirms `v32` never appears in `derive.js`. So the page labels a number "tg (short context)" on one chart (`charts.js:128`) and uses that same number, unlabelled, as the decode rate for a 16K-deep turn on the next.
Sensitivity, substituting each platform's own `at32k` (all five confidence `"m"`, same source/engine/quant as their `short` per `decodeNote`): pro6000 dense 38.5s→64.0s (+66%), rtx5090 dense 35.2→48.6 (+38%), rtx5090 moe 9.8→19.5 (+100%), pro6000 oss120b 9.1→13.0 (+44%), m3ultra dense 84.4→116.3 (+38%). Only 5 of 24 platform×arch cells carry `at32k`, so this is a coverage gap as much as a bug. **Fix:** interpolate to `atCtx` and set `est: true` where `at32k` is absent, or relabel the bar "Generation (2K tokens, short-context decode rate — not depth-adjusted)" and drop the depth claim from the caption.

**C2. "That growth is *exactly* the slope of the cold prefill curve" is an unvalidated modeling assumption, and it is measurably wrong on the one rig where it can be tested.** `data/README.md:227-232` and the identical comment at `assets/derive.js:107-121`, implemented in `marginalSegments()` (:122-146).
The identity holds only if a warm append of N tokens costs the same per token as tokens in positions [n₁,n₂] of one long cold prefill. It does not: a cold long prefill runs at full batch and amortizes per-request overhead across many ubatches; a 2K warm append does neither.
First-party, same rig/engine/model/KV-dtype/FA on both sides, so no measurement confound is available. Cold (`cache_n == 0`): 968.2 t/s at 1-4K, 1214.5 t/s at 4-16K. Differencing exactly as `marginalSegments` does: T(2048) = 2.115s, T(8192) = 6.745s → derived marginal = 6144/4.630 = **1327 t/s**. Direct measurement of that same quantity from 7,700+ warm-append events (`cache_n > 0`) at <8K depth: **881 t/s** (256-1K appends), **991 t/s** (1-4K appends). Differencing overstates the real marginal append rate by **1.34-1.51×**. Robust to segment choice: [1024,4096]→1327, [1000,16000]→1235, [4000,8000]→1629, [512,4096]→1223 — every choice exceeds the measured band.
In-repo corroboration of the mechanism: `platforms[id=pro6000].perf.oss120b.prefill` is the file's only rising row (512:20000 → 4096:24000); `marginalSegments` returns **24,706 t/s** for that segment — above any throughput in the row — and `index.html:185` attributes that rise to "short-context kernel launch overhead". The derived "attention marginal cost" there is measuring launch overhead. (That segment is computed but not rendered; `marginalRateAt` is only called at `STEADY_STATE_AT_CTX = 16384`.)
**Fix:** downgrade "exactly" to a stated assumption; add a per-checkpoint field recording measurement kind (llama-bench `-p N` whole-prompt average vs `-p 512 -d N` fixed-batch-at-depth); note that differencing a whole-prompt curve cancels per-request overhead the real append still pays.

The 10× ceiling (5200/480 = 10.8×) rests entirely on m3ultra's `"i"` value whose own note says "MoE prefill modeled". Worse under the page's own vocabulary — `verdicts.js:104` calls R9700 and V100 "a single discrete GPU" — the sign inverts for three discrete platforms: DGX Spark (2059) out-prefills pg199 (1130), b70 (527) and v100 (470); Strix Halo (900) beats the latter two. **C4. `decode.at32k`'s confidence code is discarded and then asserted as "measured" at four render sites.** `assets/data.js:53` reads it through `measurement()` (returns `{v,c}`); `:60` stores `v32: at32k.v` and drops `.c`. **D1. `units[id=arc_b70].compute.values.fp16 = 45.88` (`:399`) is the vector-engine rate while `int8 = 367` (`:400`) is the XMX rate — 4× understated.**

Cross-catalog: int8/fp16 = 2.0 for 15 units, 1.0 for the AMD RDNA3 parts; `arc_b70` alone is 8.0. **D3. `units[id=strix_halo].compute.values.fp32 = 14.85` (`:314`) excludes RDNA3 dual-issue while every sibling includes it.** 40 CU × 64 lanes × 2 FLOP × 2.9 GHz = 14.848 (exact match, so the basis is determined, not inferred); with VOPD = 29.7. ## 6. Provenance & comparability

**E1. ## 9. What this audit could not check

- **No benchmark was re-run and almost no cited URL was fetched.** Model/engine/quant attributions in `perf.*.note` were taken at face value; the audit checks whether the *labels* are internally consistent and physically possible, not whether the underlying runs happened as described. `amd.com` and the AMD MI210 brochure PDF timed out; those figures came from a third-party spec sheet plus search summaries, not AMD's own page.
- **KV dtype, flash-attention state, batch size, and engine version are recorded nowhere in the file**, so no cross-platform prefill or decode comparison in this repo can be fully validated by anyone, including this audit. Several findings are downgraded to "not comparable" rather than "wrong" precisely because that information does not exist to check against.
- **First-party grounding transfers a *method* critique, not numbers.** It is one RTX 3090, one hybrid-GDN model, with quantized KV and FA on — all three flatten the curve. It refutes "differencing gives exactly the marginal append rate" (C2) on that rig by 1.34-1.51×, and it establishes the arch classification (§1) from source. It does **not** refute a steep full-attention fp16-KV falloff on other silicon, and none of its absolute t/s figures should be pasted into this compendium.
- **Only the flagged units were spec-checked.** 28 catalog units exist; roughly six were examined. Prices, most release dates, the `multi_gpu_scaling` block, and the build/cost derivations were not audited.
- **B1 proves an inconsistency, not a resolution.** The value and its note cannot both be true; which one is wrong requires the original measurement (item 1 above).
- **B4's cause is ambiguous.** The two 800-consistent Apple cells are equally reproducible from an in-block measured anchor; "stale constant" is the likelier but not the only explanation.
